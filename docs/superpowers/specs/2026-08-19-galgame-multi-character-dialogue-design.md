# GAL 多角色同场对话设计

## 背景

现有 `TavernDialogue` 已提供完整的单角色 GAL 体验：地点背景、角色立绘、结构化分镜、流式生成、历史分支、正则显示层、互动抽屉、全屏焦点锁定和移动端底部抽屉。当前会话、提示词和分镜解析均把一个会话固定为一个 NPC，因此模型即使输出第二个角色姓名，解析器也会把她归为旁白或主角色，舞台也只能显示一张立绘。

本功能把现有单角色链路扩展成最多五名角色共享一个会话的同场 GAL 对话。主角色仍是会话的拥有者；受邀角色作为有序参与者加入同一历史、同一次模型请求和同一舞台。

## 目标

- 在与一名居民交谈时提供始终可发现的“邀约”按钮。
- 仅允许邀请好感度严格大于 70 的其他居民。
- 一个会话最多五名角色，主角色计入上限。
- 参与者列表随会话保存，并在重新打开、截断和创建分支后保留。
- 多人模式一次只发起一个模型请求；模型使用精确角色姓名输出结构化分镜。
- 舞台同时显示全部参与者立绘；当前发言者明亮、前置并带“发言中”文字标识，其他人物明显变暗。
- 玩家或旁白分镜期间所有角色统一变暗，不错误指定 NPC 发言者。
- 单角色会话的提示词、界面、精力结算、好感结算、历史、图库和错误恢复保持现有行为。

## 非目标

- 不增加新的关系值、角色卡或魔物娘好感系统。
- 不改变聊天消耗和奖励；成功对话仍只按现有逻辑结算主角色一次。
- 不并行调用多个模型，也不为每名参与者建立独立子会话。
- 不增加“请离角色”或重写历史的能力；本轮只实现邀约加入。
- 不重构酒馆中枢、图片生成、世界书编辑器或其他游戏玩法。

## 数据模型与兼容性

`ChatSession` 增加可选字段：

```ts
participantNpcIds?: string[]
```

规范化规则：

1. 主角色 `npcId` 必须位于第一个位置。
2. 只保留非空字符串并去重。
3. 最多保留五项。
4. 旧会话没有该字段时等价于 `[npcId]`。
5. 新会话显式写入 `[npcId]`。

字段不参与 Dexie 索引，因此无需数据库版本升级。`normalizeStoredSession` 负责清洗旧数据和畸形数据；`branchChat` 显式复制该字段；`truncateChatAt` 已通过对象展开自然保留。

## 邀约资格与状态转换

候选人来自 `game/data.ts` 的 15 名居民，因为只有这些居民拥有 `GameState.relationships`。候选人必须同时满足：

- 不是主角色；
- 尚未在当前参与者列表；
- 存在关系记录；
- `relationship.affinity > 70`；
- 存在可用角色卡；
- 当前参与者少于五人。

候选人按好感度降序、姓名稳定排序。好感度恰好为 70 不符合条件。

点击“邀请某角色加入对话”时，组件重新检查资格和容量，生成新的参与者列表，并把该角色卡的世界书 ID 与会话现有世界书 ID 做稳定去重合并。保存成功后立即更新舞台和会话快照；保存失败时保持原列表并在现有错误区域给出可恢复提示。生成期间禁用单项邀请操作，避免会话元数据与正在编译的请求竞争。

## 模型与提示词契约

单角色请求完全沿用当前 `REMOTE_RESPONSE_CONTRACT`。

多人请求在当前格式要求之后追加群聊契约，内容包括：

- 有序参与者姓名白名单；
- 每位参与者的角色、描述、性格、场景和示例对白；
- `speaker="npc"` 时 `name` 必须精确取自白名单；
- 每个 `<scene>` 只允许一个发言主体；
- 不要求每回合所有角色都发言，但不得让未参与角色发言；
- 玩家与旁白仍分别使用 `player` 和 `narrator`；
- 不得替玩家作决定。

示例：

```xml
<maintext>
  <scene speaker="npc" name="洛岚">先听听芙蕾雅的意见。</scene>
  <scene speaker="npc" name="芙蕾雅">药草园今天确实需要帮手。</scene>
</maintext>
```

`TavernContext.sendTurn` 从已持久化会话解析参与者卡片，合并参与者世界书，并把参与者姓名与关系摘要作为原始类型运行时变量加入编译上下文。请求审计的 `characterName` 在多人模式显示全部参与者姓名，但主角色 ID、会话 ID、图库归属和其他现有字段不变。

## 分镜解析与发言者解析

`parseGalgameSegments` 的上下文扩展为主 NPC 姓名和允许的 NPC 姓名列表：

```ts
{
  npcName: string
  npcNames?: string[]
  playerName: string
}
```

解析规则：

- 结构化 `speaker="npc"` 且 `name` 命中允许名单时，保留该精确姓名。
- 结构化 NPC 姓名缺失或不在允许名单时，安全回退为主 NPC，避免点亮不存在的角色。
- `speaker="player"` 始终规范成玩家名，防止模型借玩家帧冒充 NPC。
- 旁白始终规范成“旁白”。
- 中文署名行只有命中允许 NPC 名单时才视为 NPC；其他未知署名继续作为旁白。
- 无结构文本继续回退为主 NPC 台词，保持旧行为。

UI 通过分镜的规范化姓名匹配参与者 ID，不直接信任模型原始属性。

## UI 与交互

### 邀约入口

对话标题栏增加带 Phosphor `UserPlus` 图标和文字“邀约”的按钮，并显示 `当前人数/5`。按钮打开现有互动抽屉的“邀约”标签，而不是新增叠加模态层。这样继续复用抽屉的 Escape 优先级、焦点进入、移动端底部弹出和 `inert` 语义。

邀约标签包含：

- 当前同场角色的姓名列表和席位计数；
- 符合条件的候选卡片（立绘缩略图、姓名、身份、好感度、邀请按钮）；
- 没有合格候选人时的明确空状态；
- 五席已满时的“同场席位已满”状态；
- 保存中的禁用与状态播报。

从标题栏邀约按钮进入抽屉后，关闭抽屉把焦点还给邀约按钮；从原悬浮互动按钮进入时仍还给原按钮。

### 多角色舞台

单角色时保留现有右侧大立绘几何和动画。

两到五人时使用独立的 `.galgame-character-stage` 舞台容器：

- 参与者在可用宽度中等距排布，底部与场景对齐；
- 图像使用 `object-fit: contain`，不裁掉完整立绘；
- 角色数量通过 `data-participant-count` 或 CSS 自定义属性控制宽度；
- 说话者提升层级、亮度和轻微缩放，并显示可读的“发言中 · 姓名”标签；
- 未说话角色降低亮度、饱和度和透明度，但仍可辨认；
- 过渡只使用 `transform`、`opacity` 和 `filter`，时长 180–280 ms；
- `prefers-reduced-motion` 下取消位移和缩放过渡。

文本框头像与身份标签跟随当前 NPC 发言者。玩家或旁白发言时不把任意受邀角色标成发言者，舞台全部变暗；单角色原有姓名和文本回退保持不变。

### 响应式与可访问性

- 1440/1024/768 像素宽度下五张立绘不产生页面横向滚动。
- 375 像素宽度下舞台仍同时显示五名角色，使用更紧密的重叠与缩放；文本框保持最高阅读优先级。
- 所有新按钮触控区域不小于 44×44 像素。
- 邀约按钮、邀请动作、参与者状态均有唯一可读名称。
- 当前发言状态同时使用文字、层级和亮暗，不只依赖颜色。
- 状态保存结果使用 `aria-live="polite"`，错误使用现有 `role="alert"`。
- 键盘焦点顺序与视觉顺序一致，Escape 先关闭抽屉再退出全屏。

## 错误处理与边界

- 会话未初始化：邀约入口禁用。
- 生成进行中：候选邀请按钮禁用，已有舞台保持稳定。
- 重复点击同一候选：保存前重新规范化并去重。
- 参与者达到五人：不写入第六人并显示满席状态。
- 好感在面板打开后下降至 70 或以下：点击时重新检查并拒绝。
- 角色卡缺失：不把该角色列为候选；已存储但缺卡的参与者在渲染和请求中被安全跳过。
- 立绘缺失：显示与现有风格一致的姓名首字回退占位。
- 模型输出未知 NPC 姓名：解析回退主角色，不生成未知立绘或 DOM 标识。
- 邀约保存失败：保留原状态、显示错误、允许重试。

## 验证策略

1. 纯函数测试覆盖严格阈值、去重、主角色顺序、畸形输入和五人上限。
2. 会话仓库与分支测试覆盖旧会话迁移、保存、读取和分支复制。
3. 分镜测试覆盖两名 NPC 的结构化与中文署名解析、玩家名规范化和未知姓名回退。
4. 远程引擎测试证明单人提示不变、多人提示包含全部角色卡和精确姓名白名单。
5. 组件集成测试使用真实 Game/Tavern Provider、fake-indexeddb 和模拟 SSE：验证严格邀约资格、持久化、两张立绘、受邀角色发言点亮、主角色变暗、请求正文包含群聊契约、焦点归还。
6. 完成后运行定向测试、全部 465+ 测试、两个 TypeScript 检查和生产构建。
7. 使用可用浏览器驱动在 375、768、1024、1440 像素视口检查无横向页面滚动、五人舞台、抽屉、全屏和 reduced-motion。

## 范围保护

实现只修改会话参与者元数据、GAL 分镜/提示词、多角色对话组件、图标映射、相关样式与测试。农场经营、战斗、商店、日历、云存档、工作坊、图片生成提供商和其他酒馆编辑功能不做行为改动。
